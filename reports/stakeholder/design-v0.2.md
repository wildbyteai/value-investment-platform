## 1. 报告定位与阅读结果

建议名称：**《价值投资研究系统：业务方案、系统说明与阶段进展》**。封面副标题注明“开发阶段说明，尚未完成全部验收”。主读者为业务需求方/负责人，技术和运营人员通过附件核对实施与费用依据。

读完应能回答六个问题：

1. 系统解决什么研究工作问题，哪些事项仍由人决定？
2. 哪些页面可用，如何从公司结论回到原始依据？
3. 资料怎样形成判断、评分和策略状态，缺资料时如何处理？
4. 哪些功能已经实现或验证，哪些还在开发？
5. 为什么采用这些组件，软件费和运行费用分别是多少？
6. 下一阶段需要补什么，需求方需提供或确认哪些信息？

正文先讲业务和操作，再讲原理、选型与费用。采用 **A4 纵向 PDF 主报告 + 可编辑 Word 源稿**；截图位置用全宽占位框，组件表进入附录。0.1仅准备 Markdown 底稿、流程图源和素材计划；0.2已生成可审阅报告，尚未填入实际截图或完整验收结论。汇报型 PPT 可在有需要时另制作。

版式基线：正文11–12pt、图注约10pt；截图按最终页面尺寸检查可读性，细小表格优先裁取必要局部并保留页面出处。用文字同时标识“已实现、已验证、开发中、待接入”，颜色仅作辅助。页脚统一标注报告版本、日期、页码与“系统开发中”，流程图和截图编号与正文引用一致。

## 2. 结构与分镜建议

主报告约 18–22 页，按信息量调整，不以页数作为交付验收。

| 单元 | 需求方最关心的问题 | 内容与图文 | 建议篇幅 |
|---|---|---|---|
| RP-01 封面与摘要 | 这是什么、目前到哪一步？ | 项目定位、版本日期、开发中标识、三条当前结论 | 1–2页 |
| RP-02 业务价值与边界 | 为什么要做？ | 分散资料/口径/历史不可追溯的工作问题；系统支持的改进，不填虚构节约比例或收益 | 1页 |
| RP-03 系统全貌与角色 | 有哪些功能、谁使用？ | 七个主要页面的功能地图、五角色职责；角色兼任是已确认要求，完整管理能力仍需验收 | 1–2页 |
| RP-04 当前能力与缺口 | 哪些已可用？ | 已实现/已验证/开发中/待接入状态表；实际数据范围与来源限制 | 1页 |
| RP-05 主要界面与用户路径 | 我如何用？ | 8–12张实际截图，按“概览→公司→依据→研判→快照→策略→个人/支持”讲解，每图2–3个标注 | 4–6页 |
| RP-06 业务流程与重要规则 | 系统怎样得出结果？ | 3–4张简化流程图；公司经营/证券估值分开、时点、缺数、人工覆盖、正式状态条件 | 2–3页 |
| RP-07 架构与组件 | 为何用这些技术？ | 当前实现架构和目标扩展分图；组件作用、采用依据、费用；正文按职责分组，逐组件表放附件 | 2页 |
| RP-08 部署资源与费用 | 需要什么、花多少？ | 单机/数据库分离方案、官方价格量级示例、费用公式、排除项、预算待询价项 | 2页 |
| RP-09 下一步与需求方事项 | 怎样推进、需要我做什么？ | 下一阶段交付与验收结果、数据/账号/业务维护责任、待确认信息 | 1–2页 |
| 附件 | IT或采购如何复核？ | 组件清单、官方许可/价格来源、截图素材清单、版本与R/W/T引用 | 按需 |

主报告不要铺满技术名、代码/SQL或大段JSON。首次出现“覆盖度、正式封存、数据快照”需用业务语言解释；技术细节链接附件。需求方确认报告表达不等于批准部署、采购、数据库写入或变更已确认业务合同。

## 3. 页面说明与截图采集计划

截图用于证明某版本的页面状态和解释用户任务，不证明其业务链路已全部验收。当前导航实际来自 `frontend/src/app.tsx`，模板编辑属于公司“评分规则”标签，并非独立第八个页面。

| 素材ID | 页面/截图范围 | 配套讲解和重点标注 | 状态/采集限制 |
|---|---|---|---|
| S-01 | 今日概览 | 当前可研究公司、关键缺口、进入公司入口 | 待固定版本后只读采集；不把公司数量等同完整覆盖 |
| S-02 | 公司研究—经营质量与待补依据 | 哪些维度有依据、哪些待评估、下一步 | 截图保留真实UNKNOWN/缺口，不修图造完整高分 |
| S-03 | 公司研究—A/H证券卡片 | 一家公司与不同证券、币种/行情独立 | 参考价与正式价区分；港股未取到价格就保留说明 |
| S-04 | 财务与估值依据 | 指标来源、期间/口径、股数时效与缺项 | 原始财务值是否展示按报告受众可见权决定；默认用必要局部和说明 |
| S-05 | 固定原文阅读 | 原文、出处、修订时间/取得时间、返回入口 | 原文/引用受来源权利约束；默认不将整篇报告或商业原件放入可分享附件 |
| S-06 | 资讯与研判/研判表单 | 阅读证据→选择评价项→说明判断 | 只读展开已有记录/表单；不为截图在真实库新增判断、笔记或模拟 |
| S-07 | 已保存研究快照与历史比较 | 当次固定依据、完成阶段、前后变化 | 读取已有记录；不点击“生成新的研究预览”制造素材 |
| S-08 | 策略候选池 | 规则、预览/正式结果区别、未排期提示 | 正式真实记录为空时如实呈现；不将预览候选冒充已入选 |
| S-09 | 公司—评分规则 | 基础/行业/企业规则、来源、预览/发布入口 | 只读；若展示合成发布过程必须单独标为测试场景，不用于真实公司结论 |
| S-10 | 我的工作台 | A/H自选、个人研究上下文 | 不展示他人私人笔记/账号；本轮不新增自选或笔记 |
| S-11 | 系统支持 | 来源/任务/运行故障与权限职责 | 管理员只管授权范围；遮蔽账号、私有URL、凭证与内部诊断详情 |
| S-12 | 缺数据或失败状态，窄屏局部 | 缺项不等于零分；未完成如何继续 | 补充说明图，按已有状态取材，不为截图使真实任务失败 |

最终实际截图建议先取桌面宽度约1440px，核心路径辅以390px窄屏；固定浏览器、缩放、角色和viewport，正文每图2–3个编号标注。截图下统一写：素材ID、页面、版本/采集日期、真实/合成场景及当前能力边界。原始截图与脱敏图分开保存；原始业务像素仅留本机受限/忽略目录，不默认入Git或上传外部文档/图片服务。

素材登记至少含 `asset_id、captured_at、revision、page、role、viewport、scenario_type、caption、source_evidence、redaction、approval_scope、status`。0.2全部 S-01…12 为 **placeholder（占位，未实际采集）**，已生成明确标识的占位图片供排版。原型或AI生成界面不得冒充当前运行界面；历史截图只能标注其历史版本。

## 5. 组件与费用的呈现合同

每个主要框架/平台记录：ID、作用、采用/候选状态、具体采用依据、许可/服务费用、运行成本、官方依据、适用版本/计费条件。采用依据按“本项目需要→组件如何支持→限制/替代”书写；“很流行”只能作背景，不能取代业务和工程依据。

- 已采用：用源码、manifest/lock、迁移/工作流及验证材料证明；许可证用本地包元数据/许可正文与官方来源核对。
- 目标/候选：用03/17等设计说明，不称已上线；实际采用前验证版本、许可和接口兼容。
- 开源软件授权费为0，仍可能产生主机、运维、商业支持和改造费用；协议/接口标准本身无按次授权收费，不代表其托管服务免费。
- 付费价格写明官方来源、查询日期、币种、月/年周期、规格、包含量、税费/超量/支持/汇率等排除项。优惠价、个人数据套餐不得直接代替长期企业运行价。
- 费用分“已发生、官方价目参考、预算假设、待正式报价”，未查账单不得写实际已支出为0；未选模型不编造每token价格。
- 本轮不选定云厂商、托管地域或数据采购；对外域名访问是授权用户远程访问，不自动成为公开数据再分发服务。

需求方附件见[框架、采用依据与费用](frameworks-and-costs.md)，底层依赖核查底稿保留为[内部明细](components-and-costs.md)，公开依据见[费用核查记录](../../research/report-component-cost-basis.md)。19保留其先前组件快照与资源估算；其“两家公司/EODHD令牌尚待”等历史背景不用于本报告最新状态。

## 7. 报告本身的检查标准

这些是报告编写检查，不改变产品必选验收。

| ID | 检查/预期 |
|---|---|
| RC-01 | 每个主要页面说明“谁用、看什么、下一步、当前限制”，且与源码导航一致 |
| RC-02 | 已实现、已验证、开发中/待接入清楚；当前规模不沿用历史数字，不把测试数量相加或写成功率 |
| RC-03 | 模型建议、人工判断、经营质量、证券估值、研究预览和正式状态没有混写；缺资料不是0/否定 |

| RC-05 | 每项费用有类别/单位/状态/条件；小计可复算，未知不写0，运行成本和人员/数据费用不漏报为全价 |
| RC-06 | 外部只查询公开产品/许可/价格，不上传源码、截图、真实资料或凭证；秘密、私人对象和内部连接信息不进入报告 |
