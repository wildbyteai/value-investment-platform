# 00 产品主线（2026-10-07 用户确认）

> 本文是仓库的**第一阅读入口**：先用大白话讲清楚这个系统到底做什么、用户每天在哪里做什么，再去读 01…20 的细节。
> 状态说明：本文记录的是**已确认的产品方向与设计**，不是已经做好的功能。每一节末尾单独写明“设计 / 已实现 / 已验证”三种状态，三者不能混为一谈。
> 本文不改任何代码、配置（config/*.json）或业务数字；文中提到的门槛数值都以配置文件为准，这里只做引用说明。
> 决策记录见 [ADR-0005](./adr/0005-product-mainline-and-strike-zone.md)。

## 1. 一句话

每天大量资讯涌进来，系统把它们对到具体公司、判断影响多大，结合公司本身的生意质量和价格，**只把落在我们“击球区”里的机会挑出来盯住**，其余的记录在案但不打扰人。

## 2. 底层逻辑：四层

用户原话归纳为四层，自下而上：

| 层 | 做什么 | 产出 |
|---|---|---|
| ① 新闻资讯 | 每条资讯关联到哪些公司、关联程度多高、对公司影响是好是坏、有多大 | 资讯 → 公司的“关联度”和“影响分” |
| ② 公司 | 看懂公司：商业模式、财报、与它相关的资讯，经过分析后给出各项打分 | 公司档案 + 经营质量各维度打分 |
| ③ 价值投资策略逻辑 | 用一套明确、可解释的价投规则判断：这家公司我们看得懂吗、生意好吗、价格便宜吗 | 每只证券在不在“击球区” |
| ④ 击球区 | 不同事件影响不同公司，就像投手投出不同的“球”；**只处理落在击球区内的球**，并对它们做监控告警 | 进入/离开击球区、区内风险的变化记录（以后再加提醒推送） |

一句话串起来：**资讯是球，公司是被影响的对象，策略是我们的打击纪律，击球区决定挥不挥棒。**

## 3. 四个菜单 + 设置

用户日常只看四个菜单，后台事务放进“设置”。下表说明每个菜单里用户做什么，以及它吸收了现在哪些页面和后端模块（现有七个页面见 [docs/18 §3.1](./18-ux-and-copywriting-redesign.md)）。

| 菜单 | 用户在这里做什么 | 吸收的现有页面 | 对应的现有后端模块 |
|---|---|---|---|
| **资讯雷达** | 看今天进来了什么；每条资讯关联了哪些公司、关联度和影响分；确认或修改模型的建议 | 今日概览（资讯部分）、资讯与研判 | 资讯记录 item 与修订/观察、资讯—公司关联 item_company_link、判断中的影响 judgment impact、自动审核 decision_service |
| **公司档案** | 看懂一家公司：生意、财报、相关资讯时间线、各项打分及依据；做人工覆盖 | 公司研究、研究快照、我的工作台（研究笔记） | 评分 scoring_service、参考研究 reference_research、研究运行 research_pipeline、财报与股本导入 |
| **策略（划击球区）** | 维护“能力圈”名单、查看/模拟价投规则门槛，看哪些证券在甜区、边角球、区外 | 策略候选池 | strategy_service、状态机 state_machine |
| **监控告警** | 看进入/离开击球区、区内或边角球公司出现硬风险的记录；以后在这里接收提醒 | 今日概览（变化部分）、我的工作台（自选关注） | 变化记录 change_record；封存 sealing_service、seal_worker |
| **设置** | 数据源、后台任务、账号与权限 | 系统支持 | source_registry、worker/outbox、RBAC |

**后台保证不进日常界面**：封存（seal）、修订号（revision）、冻结清单（manifest）、hash 校验这些机制继续在后台保证“结果可追溯、可重放、不被偷改”，但日常界面不再出现这些术语；用户看到的是“这个结论基于哪天哪些资料”“能不能回看当时的依据”。

状态：设计已确认；菜单尚未重建（计划 R4）。现有七个页面仍是当前实际界面。

## 4. 第一层输入：资讯从哪里来

### 4.1 现在的做法（人工）

目前由人设置定时任务，从网上抓取资讯，每天生成 Excel 文件，共 6 条资讯线：

1. AI科技行业每日动态
2. AI科技行业重要动态
3. 创新药每日动态
4. 重点创新药公司动态——监控 诺诚健华（688428.SH / 09969.HK）、百济神州（688235.SH / 06160.HK / BGNE）、英矽智能（03696.HK）、信达生物（01801.HK）
5. 全球新消费新娱乐动态
6. 企业家访谈摘要（含★价值评级）

合计约 30 条/天。

### 4.2 现在的问题

- 各条线 Excel 的列不一样，无法直接合并；
- 只有“重点创新药公司动态”带股票代码，其他线需要人去对公司；
- 跨线重复：同一件事出现在两条线里（例如 三星HBM、OpenAI DevDay 各出现在两个文件）；
- 有“今日无重要动态”这类占位行，不是真实资讯。

### 4.3 目标做法（设计）

1. **系统接管定时任务**：每条资讯线配置为“主题 + 关注公司名单”，由系统按时采集，不再依赖人手设的定时器。
2. **统一成一种资讯记录**：标题、摘要、来源、原文链接、发布时间、采集时间、主题线。占位行直接识别并跳过。
3. **去重合并成“事件”**：同一件事无论来自几条线，只算一个事件；后续的市场反应挂到原事件下面，不重复计分。例：诺诚健华 9/30 的股价反应，挂到 9/24 与礼来合作这一事件下。
4. **模型给建议，研究员拍板**：模型提出“关联哪些公司 + 关联度 + 影响分”；影响分为带正负号的 -1 到 +1（负面为负），沿用 [docs/02 §关联度与影响值](./02-business-design.md) 与 [docs/11](./11-templates-automation-and-roles.md) 已确认的合同；研究员可确认或改写，人工有效覆盖优先。
5. **Excel 导出保留**：方便人继续用熟悉的方式浏览。

状态：设计；**未实现**（计划 R5）。当前系统只有显式命令触发的真实资料导入，没有接管这 6 条资讯线。

## 5. 击球区：什么时候挥棒

### 5.1 来源

巴菲特在伯克希尔股东信中引用棒球手泰德·威廉斯（Ted Williams）的《The Science of Hitting》：威廉斯把好球区切成 77 个格子，只在自己最有把握的“快乐区（happy zone）”挥棒（[1994 年信](https://www.berkshirehathaway.com/letters/1994.html)谈 happy zone，[1997 年信](https://www.berkshirehathaway.com/letters/1997.html)谈 77 格）。巴菲特指出，投资和棒球不同——**不挥棒不会被判三振出局**，所以可以一直等，等到又肥又正的好球再出手。

### 5.2 三个条件，缺一不可

一只证券只有**同时满足**下面三条，才算“在击球区”：

**(a) 能力圈——我们看得懂**
- 公司在研究员维护的“能力圈名单”（行业/公司白名单）上；并且
- 评分覆盖度 ≥ 0.8，即我们手里有足够证据理解它。

**(b) 好生意——公司本身够好**
- 经营质量分达到入选门槛、财务门槛通过、没有已确认的硬风险。
- 直接复用已发布的标准策略门槛，**以 [config/strategy-standard-v1.json](../config/strategy-standard-v1.json) 为准**。截至本文写作时配置为：入选质量 ≥70 / 保留 ≥65、覆盖度 ≥80%、TTM ROE ≥10%、三年经营现金流/净利润 ≥80%、净负债/EBITDA ≤2.0。此处只是转述，配置变了以配置为准，本文不另立数字。

**(c) 好价格 / 安全边际——价格明显低于内在价值**
- v1：内在价值尚未计算，暂用现有“证券估值分”的入选门槛（≥60，保留 ≥50，同样以配置为准）作为替代。
- 安全边际 = (内在价值 − 价格) / 内在价值，v1 以 `1 − 市盈率TTM / 合理市盈率(15)` 计算，**甜区要求 ≥30%**（用户 2026-10-07 同意按标准逻辑先定、后续调整；见 ADR 0007、config/strike-zone-v1.json）。

### 5.3 三种区域

| 区域 | 条件 | 系统怎么处理 |
|---|---|---|
| **甜区** | (a)(b)(c) 全满足 | 按现有规则，连续 2 个正式收盘（FINAL）交易时段满足后进入候选池 |
| **边角球** | (a)(b) 满足，价格还没到 | 进“观察名单”，只盯一件事：价格是否达到门槛 |
| **区外** | 其他情况 | 照常记录，**从不告警** |

补充规则：
- A 股与港股（A/H）是两只证券，分别判断，价格不相加。
- 硬风险一经确认，立即否决（直接出区），不等两个交易时段。

状态：设计已确认；能力圈、区域划分与安全边际已在 R3 实现为只读分类（`/api/strike-zone`），现有已实现的是标准策略门槛、两时段确认和硬风险规则的代码，真实环境中尚无正式封存的评估（真实封存数 0）。

## 6. 告警口径

- **通知后置**：不在当前开发切片内（与 [docs/11](./11-templates-automation-and-roles.md) “通知后置”一致）。
- 将来做的时候，渠道 = **邮件 + 站内**。
- 只在三种情况触发：**进入击球区、离开击球区、区内或边角球公司出现硬风险/重大负面事件**。
- 区外的资讯只记录，不提醒。
- 现有的变化记录（change_record）仍是唯一的事实来源；通知只是在它之上的“投递”，不另起一套判断。

状态：设计；**未实现**（计划 R6）。
